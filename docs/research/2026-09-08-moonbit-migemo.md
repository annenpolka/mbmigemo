**MoonBitはブラウザ向けMigemoの実装に適しているか**

調査日：2026年9月8日。公式ドキュメント、開発元の公開記事、実装リポジトリ、ブラウザ実装元の情報を確認した。以下では公開情報で確認できた事実と、そこからの設計判断を区別する。MoonBit版Migemoのビルド、容量測定、速度測定は実施していない。

ブラウザでの配布容量と、同じ処理を複数の実行環境で使うことを優先するなら、MoonBitは最初に試す価値があるというのが今回の判断。JavaScriptとWasm GCの両方へ出力できることが効く。一方、C ABI経由で各言語やエディタから呼ぶlibmigemoの代替まで一度に目指すなら、現行のnativeライブラリ出力の制限が選定上の障害になる。

MoonBitは、静的な型付けと自動メモリ管理を持ち、複数のバックエンドへコンパイルする言語。今回重要なのは、実行先によってメモリ管理方式が異なる点である。通常のWasmとCバックエンドでは参照カウント、Wasm GCとJavaScriptではホストのGCを使う。[公式FFI仕様](https://docs.moonbitlang.com/en/latest/language/ffi.html)

| 出力先 | 実行の形 | Migemoでの使いどころという設計判断 |
| --- | --- | --- |
| JavaScript | JavaScriptエンジンが実行 | Web向けの基準実装。Wasmの追加機能を必要としない配布先にも対応しやすい |
| Wasm GC | ホストのGCを利用するWasm | 小さい実行コードと文字列の受け渡しを重視する構成 |
| 通常のWasm | 線形メモリを使うWasm | Wasm GCのない実行環境を別途対象にするときに検討 |
| native | Cバックエンドによるネイティブ実行 | CLIを作る選択肢。共有ライブラリとしての配布には後述の制限がある |

これらは現在のビルド対象に含まれる。ただし、同じソースを共有するには依存パッケージも各対象をサポートする必要があり、OSやブラウザとの接続部分には対象別の実装が必要になる。JavaScript出力はES Modulesなどの形式を選べる。[パッケージ・ビルド設定](https://docs.moonbitlang.com/en/latest/toolchain/moon/package.html)

小型化への期待には仕組み上の根拠がある。Wasm GCでJS String Builtinsを有効にすると、JavaScript側の文字列を使い、ホストの文字列操作へ接続できる。開発元の2024年11月の例は、文字列の連結と出力をホストへ任せることでWasm本体を小さくしている。自前の文字列表現と変換処理を必要とする構成に比べ、ブラウザで「文字列を受け取り、文字列を返す」部品には有利になり得る。[JS String Builtinsの公式解説](https://www.moonbitlang.com/blog/js-string-builtins)

その記事の公開値は次のとおり。いずれもMigemoの測定値ではない。

| 公開例：文字列の連結・出力・返却 | Wasmファイルのバイト数 |
| --- | ---: |
| MoonBit / Wasm GC / JS String Builtins | 182 |
| 上記をwasm-opt -Ozで最適化 | 117 |
| Rust / wasm-bindgen / 記事中のサイズ最適化設定 | 12,534 |

ここから「MoonBit版Migemoも数百バイト」「Rustより常に何十倍も小さい」とは言えない。比較対象のRust実装はformat!やprintln!を含み、ホストへ処理を移す度合いも違う。数字は接続用JavaScript、辞書、ブラウザのランタイムを含む総容量ではなく、転送圧縮後の容量でもない。wasm-optはコードの最適化であり、gzipやBrotliとは別である。[比較のコードと条件](https://www.moonbitlang.com/blog/js-string-builtins)

Migemoへの示唆は、入力と出力が短い文字列なので、この接続方式を活用しやすそうだという点にある。実際、公式にはMoonBitのMarkdown処理をWasmからJavaScriptへ公開する例がある。ただし複合型やResultはそのままJavaScriptのオブジェクトとして扱えるとは限らず、公開用のラッパーを用意している。Migemoでも公開APIを少数の操作に絞るのがよい。[MarkdownライブラリをJSから呼ぶ公式例](https://www.moonbitlang.com/blog/call-wasm-from-js)

容量を論じる際は、実行コードと辞書を別々に見る必要がある。既存のjsmigemoは圧縮的なバイナリ辞書を別ファイルとして読み込む。確認時点のmigemo-compact-dictはGitHub表示で1.32 MBだった。これはファイルの大きさであり、転送量や実行時メモリではない。[jsmigemoの利用例](https://github.com/oguna/jsmigemo)、[辞書ファイル](https://github.com/oguna/jsmigemo/blob/master/migemo-compact-dict)

したがって、同程度の辞書を使う場合、実行コードだけを小さくしても総ダウンロード量の改善は限定的になる可能性がある。最初の検索までの時間には辞書の取得、デコード、索引の構築、メモリへの配置も関係する。言語を変えても同じ辞書のバイト数は減らない。辞書の形式を共通化し、コードと別にキャッシュできる構成をまず採用したい。

辞書処理については、MoonBitにBytesや整数演算があるため、既存のバイナリ形式を読む実装は検討できる。文字列はUTF-16コード単位を基本とするため、UTF-8の辞書オフセットと文字列のインデックスを同一視してはいけない。[言語の基本型・文字列仕様](https://docs.moonbitlang.com/en/latest/language/fundamentals.html)

設計案としては、辞書を大量のノードオブジェクトへ展開する方法と、バイト列・ビット列・オフセットで保持する方法を区別したい。小さい辞書を小さいまま保持できるかは、Wasm GCの採用だけでは決まらない。特にJavaScript出力で、BytesはUint8Arrayに対応するが、一般のFixedArrayがすべてTypedArrayになるわけではない。また、Wasm GC側のバイト配列とJS側のUint8Arrayの受け渡しは、文字列と同じ仕組みとは限らない。[型とFFI表現](https://docs.moonbitlang.com/en/latest/language/ffi.html)

このため、辞書は初期化時にまとめて渡し、探索中に1バイトごとにJSとの境界を越えない設計を試す。読み込み時にコピーが発生する場合は、その時間と一時的なメモリ増加も測る。GCのコードをホストに任せられることは、辞書の保持コストやGC停止時間がなくなることを意味しない。

ブラウザ互換性では、通常のWebAssembly、Wasm GC、JS String Builtinsを区別する必要がある。JS String Builtinsは専用のコンパイルオプションで有効にする機能で、WebAssemblyオブジェクトの存在確認だけでは足りない。[MDNの機能解説](https://developer.mozilla.org/en-US/docs/WebAssembly/Guides/JavaScript_builtins)

Safariについては古い未対応情報をそのまま使えない。WebKitの2026年7月27日の説明では、Safari 26.2で通常のcompile()/instantiate()経由のJS String Builtinsに対応し、26.6ではStreaming版にも同じオプションが追加された。したがって26.2〜26.5を対象に含めるなら、ストリーミング経路だけを実装するのは不十分になる。[Safari 26.6の公式リリース説明](https://webkit.org/blog/18178/webkit-features-for-safari-26-6/)

ここからの設計判断は、同じコアからJavaScript版とWasm GC版を作り、必要な機能を確認してロードする方法が扱いやすいというもの。ただし、最初から両方をダウンロードすると配布量が増える。選択した実装だけをロードし、JS版を基準としてWasm GC版の利点が実測できた環境へ提供する。古いWebViewまで対象にするなら、生成JSが使う構文・組み込みAPIについても動作確認する。

速度については、MoonBitがCやRustより速いというMigemo固有の根拠は今回得られなかった。公式のJSバックエンド紹介には速度比較があるが、Iterator処理やJSON5パーサーの特定実装を比較したもの。Migemoの辞書探索にその倍率を適用することはできない。[JSバックエンド紹介と比較条件](https://www.moonbitlang.com/blog/js-support)

推測として、Migemoの体感性能には辞書の配置、短い前方一致での候補数、正規表現の生成方法、初期化、文字列の割り当てが効く。MoonBitの言語機能だけでは優劣を決められない。また、生成した正規表現をブラウザでコンパイルし文書を検索する時間は、Migemoの展開処理とは別に測る必要がある。ブラウザ向けには正規表現エンジンを追加で同梱せず、まずJavaScriptのRegExpを使う構成を提案する。

「汎用性」の判断を左右するのはnative側の境界である。現行の公式文書では、nativeバックエンドはforeign_libraryパッケージをリンク可能なライブラリ成果物として出力することをサポートしておらず、.dllや.soも明示的に含まれている。C関数をMoonBitから呼べることと、MoonBit実装をCの共有ライブラリとして配布できることは別の能力である。[nativeライブラリ出力の制限](https://docs.moonbitlang.com/en/latest/toolchain/moon/package.html)

そのため、ブラウザ・JavaScript実行環境・CLIでコアを共有したい用途では有望だが、既存のlibmigemo利用先へ同じC ABIで差し込むことが必須なら、現時点ではCやRustを優先する判断になる。生成Cに独自のビルドやランタイム接続を加える余地は別途検証できるものの、今回それが完成済みの配布経路だとは確認していない。なお、既存のC/Migemo自身にもEmscriptenによるWasm向け構成がある。既存挙動の維持が最優先なら、再実装の費用と合わせて評価したい。[C/Migemo公式リポジトリ](https://github.com/koron/cmigemo)

成熟度についても条件がある。調査時のドキュメント表記はv0.10.11、確認した最新の公式リリース記事は2026年8月19日のv0.10.9だった。6月の記事では1.0の目標を2026年第3四半期とし、調整の可能性を明記している。1.0が出たとみなして採用判断はしない。[v0.10.9の更新](https://www.moonbitlang.com/updates/2026/08/19/index)、[1.0の予定を示すv0.10.0の記事](https://www.moonbitlang.com/updates/2026/06/08/moonbit-0-10-0-release)

8月の更新にも構文・標準ライブラリの移行が含まれる。また、同更新では既定のターゲットがwasmになったと記されている。評価用のビルドではコンパイラと依存の版を固定し、wasm-gcやjsを明示して比較する。古い記事の設定や既定値をそのまま使わない。[v0.10.9の言語・ツール更新](https://www.moonbitlang.com/updates/2026/08/19/index)

コンパイラの公開リポジトリはMoonBit Public Licenseを説明しており、生成物と利用者のMoonBitソースは利用者がライセンスを選べるという例外を掲げている。コンパイラ自体をMITやApacheと同じ条件だとは扱わない。コンパイラの改変・配布を必要とする場合と、アプリを作る場合を区別する。[コンパイラ公式READMEのライセンス説明](https://github.com/moonbitlang/moonbit-compiler)

今回確認した範囲では、流用できるMoonBit製Migemo実装は見つからなかった。したがって「MoonBitへ移植する」は、既存CをそのままMoonBitコンパイラへ渡す作業ではなく、辞書読み出し・ローマ字変換・候補展開・正規表現生成を実装する作業になると考える。未知の言語の採用費用はあるが、処理範囲を純粋なライブラリに絞るなら、Webフレームワーク全体を移すより依存を少なく保ちやすい。

提案する最初の構成は、MoonBitの共通コアにローマ字処理・辞書探索・正規表現生成を置き、JavaScript側に辞書取得・ロード先の選択・RegExpによる検索を置くもの。公開APIは、概念的には「辞書からインスタンスを作る」と「入力文字列からパターン文字列を得る」の二つを中心にする。これは提案するAPIであり、既存パッケージの実在するシグネチャではない。正規表現の方言差が必要になった段階で、出力形式の選択を追加する。

試作の目的は言語の順位づけではなく、同じ機能がどの構成で小さく、十分速く動くかを確かめること。比較するのは既存jsmigemo、MoonBitのJS版、MoonBitのWasm GC版、必要ならRustのWasm版。辞書の語彙・形式・入力・出力の意味をそろえ、アルゴリズムが異なる場合はその差を記録する。

| 確認項目 | 測り方・比較条件 |
| --- | --- |
| 挙動 | 同じ入力に対する検索結果を比較。正規表現文字列の完全一致だけで判定しない |
| 配布容量 | コード、接続用JS、辞書を分け、未圧縮とgzip/Brotli後を記録 |
| 初回待ち時間 | 取得、コンパイル、辞書の準備、最初の問い合わせを分ける |
| 入力中の応答 | 辞書初期化後の展開時間の中央値・p95・p99と、生成パターン長を記録 |
| 検索全体 | 正規表現のコンパイルと同一文書への照合も別に計測 |
| メモリ | 辞書の保持量、一時コピーを含むピーク、連続入力後の割り当て傾向 |
| 環境 | 対象のChrome・Firefox・Safari・WebViewと実機を明記 |

入力には短い前方一致、辞書にない語、長い語、n/nnやshi/siの扱い、入力途中からの削除、全角・半角、濁点の表現、補助平面の文字、正規表現のメタ文字を含める。受け入れる表記ゆれは既存実装との互換要件として決める。Workerへ移す場合は初期化とメッセージ往復の時間も含め、短い問い合わせが本当に改善するかを確認する。

私の採用判断は、Web中心で新しくコアを作るならMoonBitを先に試す、というもの。JS版を比較の基準にし、Wasm GC版は容量と待ち時間の利点を測ってから配布先を決める。C ABIでの幅広い組み込みを最優先するなら、nativeライブラリ出力の制限が解消されるか、独自の接続方法が検証できるまではC/Rustを選ぶ。今回の資料だけではMoonBit版Migemoの容量上限や、C/Rustに対する速度の倍率は提示できない。
